# 后续版本怎么升级

通常不需要重做汉化。原作者网页及本项目新增的中文、RPC 适配层、构建工具可以继续使用；每次升级主要是核对变化和重新验证。没有启用无人值守更新或定时发布。

## 三种情况

| 上游变化 | 需要做什么 |
| --- | --- |
| 仅 SynoCommunity 套件修订号变化，Transmission 接口不变 | 锁定新原包、核对套件结构和安装脚本，重新打包并验证。 |
| Transmission 增加字段、设置或调整 RPC | 对照对应版本的 `docs/rpc-spec.md`，更新适配层和相关参数页、中文提示，运行隔离测试。 |
| 大版本或网页框架发生显著变化 | 需要重新评估兼容边界，可能要调整部分实现；原有汉化成果仍可参考。 |

## 维护步骤

1. 更新 `sources.lock.json` 的原包地址、版本和 SHA256；保留旧记录。校验值须独立核对，不能把下载后的任意值直接当成可信来源。
2. 阅读新版本发行说明和对应版本 RPC 文档，比较 `INFO`、安装/升级脚本、网页目录及动态库清单。
3. 修改 `src/rpc-compat.js`、`tools/build_twc.py`。新设置既要有中文标签，也要确认保存后服务端实际接受；不要只看页面显示。
4. 同步 `tools/package_release.py` 中的版本、时间和更改日志，以及网页版本。采用高于已发布包的合法版本号，避免 DSM 拒绝升级。首版的 `3101` 是自定义修订号，不是官方修订号，不能直接假定后续官方 `32` 可以覆盖它。
5. 先保留旧 `release-manifest.json`。新源码首次构建出现旧成品哈希不匹配属于预期保护；审核新产物后再更新该文件，重新运行构建确认稳定。
6. 在没有用户配置、任务和下载目录的隔离实例运行 `tests/rpc-integration.mjs`，检查页面、设置保存、任务状态，以及网页恢复脚本。不要对日常使用的下载服务运行此测试，它会创建测试任务并更改全局设置。
7. 备份测试 NAS 的套件、配置和任务记录，再用 DSM 执行真实升级，核对任务及账号保留、服务启动和登录。
8. 更新安装说明、验证范围、第三方源码与许可证、校验文件，并发布新的 Release。保留上一版以供回退。

## 套件更新可能覆盖中文网页

本项目把中文网页放在套件自带的网页目录中。以后安装官方 SPK 时，该目录可能被替换为官方网页。保留网页包和恢复说明，升级后应重新核对兼容性，再安装相应的中文网页包；不要盲目把旧网页覆盖到任意新版本。

## 测试入口

`node tests/rpc-integration.mjs` 仅用于隔离实例。设置 `TWC_TEST_RPC_URL` 指向映射到本机的测试 RPC，并设置 `TWC_ALLOW_MUTATING_TESTS=1` 显式开启。测试还会核对下载目录为 `/tmp/twc-downloads`、初始任务为空，减少误用日常服务的风险。原作者固定源码需要先通过构建脚本下载。
